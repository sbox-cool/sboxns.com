Install in one command

On a Linux VPS or a Mac, the installer creates a project and API keys, gets a free HTTPS name and starts the service.

  • Checks the download against the release SHA256SUMS
  • Free name under sboxns.com, or your own domain
  • Prints your project ID, keys and HTTPS address
Full install guide

Public IP

curl -fsSL https://github.com/sbox-cool/sbox-network-storage-server/releases/latest/download/install.sh \
  | sudo env SBOX_NS_PROJECT="My Game" SBOX_NS_DNS=1 \
      SBOX_NS_ACME_EMAIL="you@example.com" SBOX_NS_ACCEPT_LETSENCRYPT_TERMS=1 sh

For a Linux VPS, or a Mac with public or port forwarded ports 80 and 443. Your name looks like NAME.n1.sboxns.com and players connect straight to your IP. SBOX_NS_ACCEPT_LETSENCRYPT_TERMS=1 accepts the Let's Encrypt subscriber agreement; the email is the certificate contact.

No open ports

curl -fsSL https://github.com/sbox-cool/sbox-network-storage-server/releases/latest/download/install.sh \
  | env SBOX_NS_PROJECT="My Game" SBOX_NS_TUNNEL=1 sh

For a home Mac or any host without open ports. No sudo needed. On a Mac the installer starts a per-user launchd service; on Linux without sudo it starts nothing, so run sbox-ns start afterwards (or install with sudo to get a systemd service). A Cloudflare Tunnel connects out from your machine and your name is NAME.sboxns.com. DNS and tunnel are mutually exclusive. Without sudo, run later sbox-ns commands without it too.

Windows

irm https://github.com/sbox-cool/sbox-network-storage-server/releases/latest/download/install.ps1 | iex

In PowerShell. Without administrator rights it installs to %LOCALAPPDATA%\Programs\sbox-ns and adds it to PATH; as administrator it installs to Program Files for all users, then runs sbox-ns setup. SBOX_NS_PROJECT and SBOX_NS_TUNNEL work without administrator rights; only SBOX_NS_DNS needs an elevated PowerShell. The installer does not start a service: run the sbox-ns start command it prints.

Own domain

curl -fsSL https://github.com/sbox-cool/sbox-network-storage-server/releases/latest/download/install.sh \
  | sudo env SBOX_NS_PROJECT="My Game" SBOX_NS_PUBLIC_URL="https://ns.example.com" sh

Use your own domain, then add a certificate or an HTTPS reverse proxy. Docker and PostgreSQL are in the self-hosting guide.

One backend. Any host.

Your game servers stay thin. Whether a player hosts the session or you run a dedicated box, currency, XP, items and scores change through endpoints on your Network Storage server when collections are set to endpoint access.

Hosting models

Player-hosted

A player runs the listen server from their own game. It only holds the public key, so it can call public endpoints but not dedicated-only endpoints or the management API. The cheapest way to start; the rules still run on your backend.

Public key

Dedicated

Your own box runs the game server with a secret key. It can call dedicated-only endpoints and the management API. Use it for tournaments, seasons and anything worth protecting.

Secret key

Hybrid

Players host day-to-day sessions while your dedicated box runs special modes. One project serves both: public endpoints for everyone, secret-key endpoints for your box.

Both

The dashboard's authority check lists any game data a client could still change directly, so you close the gaps before players find them.

Game values: one set of numbers for game and server

Define weapons, items, prices and tuning once. Your game loads them in one call and shows them instantly; your endpoints check claims against the same numbers.

Game values guide

Predict on the client, check on the server

Show a zombie's health as 20 × level before the fight. The endpoint computes the same number from the same value and rejects a kill that does not add up.

Versioned with every build

Publishing a build snapshots its game values. Players on a supported previous build keep theirs, so new items do not reach builds that cannot load them. Or push straight to live; supported snapshots are not overwritten.

One request, then instant

Load the whole item catalog when the game starts. Lookups after that are local: no round trip per item, no lag, less load on your server.

Change a value live

Edit them in your dashboard or over the API. Live requests use the new numbers at once, with no game update; builds pinned to a supported older revision keep theirs.

Game values (YAML)
items:
  - id: combat
    type: group
    entries:
      zombie_hp_per_level: 20
      max_clock_skew_ms: 2000
  - id: weapons
    type: table
    columns:
      - key: weapon_id
        type: string
      - key: damage
        type: number
      - key: fire_interval_ms
        type: number
    rows:
      - weapon_id: pistol
        damage: 15
        fire_interval_ms: 300
      - weapon_id: shotgun
        damage: 45
        fire_interval_ms: 900
In your game (C#)
var gv = await NetworkStorage.GetGameValues();
if ( !gv.HasValue ) return;
var combat = gv.Value.GetProperty( "groups" )
    .GetProperty( "combat" ).GetProperty( "values" );

// Predict before the fight; the server checks the same number
int zombieHp = combat.Int( "zombie_hp_per_level" ) * zombieLevel;

var weapons = gv.Value.GetProperty( "tables" ).GetProperty( "weapons" )
    .ReadList( "rows", r => (Id: r.Str( "weapon_id" ), Damage: r.Int( "damage" )) );

Game values are read-only from game code. Change them in your dashboard, over the API, or with a coding agent you allow.

Build the economy once. Enforce it everywhere.

Collections hold the data and endpoints hold the rules. Both are YAML you push from the s&box editor or write in the dashboard.

Shops, crafting and inventories

Prices live on your server in game values. The endpoint looks up the price, checks the balance, then charges and adds the item in one write.

  • The game sends an item id, never a price
  • Gold is a ledger field: every change records a reason
  • INSUFFICIENT_GOLD returns before anything is written
YAML Source reference
endpoints/purchase-item.endpoint.yml
kind: endpoint
id: purchase-item
method: POST
input:
  type: object
  properties:
    item_id:
      type: string
steps:
  - id: player
    type: read
    collection: players
    key: "{{steamId}}"
  - id: item
    type: lookup
    source: values
    table: shop_items
    where:
      field: item_id
      op: "=="
      value: "{{input.item_id}}"
  - id: can_afford
    type: condition
    check:
      field: player.gold|0
      op: ">="
      value: "{{item.cost}}"
    onFail:
      status: 400
      error: INSUFFICIENT_GOLD
  - id: pay_and_add
    type: write
    collection: players
    key: "{{steamId}}"
    ops:
      - op: inc
        path: gold
        valueExpression: "0 - {{item.cost}}"
        reason: "Purchased {{item.name}}"
      - op: push
        path: inventory
        value:
          item_id: "{{input.item_id}}"

Leaderboards that rank real scores

With collections set to endpoint access, scores change only through your endpoints, so the board ranks what the server accepted. A leaderboard query ranks players by any numeric field and caches the result.

  • Rank by xp, kills, wins or any number
  • Cached for 60 seconds: a busy board costs one query a minute
  • Public, or restricted to your dedicated server
YAML Source reference
queries/top_xp.query.yml
kind: query
id: top_xp
name: Top XP
type: leaderboard
sources:
  - collectionId: players
    alias: player
config:
  field: xp
  order: desc
  limit: 10
  fields:
    - name
    - xp
    - level
    - tier
cache:
  ttlSeconds: 60
requiresSecretKey: false

Daily rewards, quests and XP

Dates come from the server clock and amounts from game values, which limits what a changed device clock or an edited request can earn.

  • One claim per UTC day, enforced by a condition step
  • Tune rewards in game values without a game update
  • ALREADY_CLAIMED (409) on a second claim
YAML Source reference
endpoints/claim-daily.endpoint.yml
kind: endpoint
id: claim-daily
method: POST
steps:
  - id: player
    type: read
    collection: players
    key: "{{steamId}}"
  - id: not_claimed
    type: condition
    check:
      field: player.last_daily
      op: "!="
      value: "{{_dateUTC}}"
    onFail:
      status: 409
      error: ALREADY_CLAIMED
  - id: claim
    type: write
    collection: players
    key: "{{steamId}}"
    ops:
      - op: inc
        path: gold
        value: "{{values.rewards.daily_gold}}"
        reason: Daily login
      - op: set
        path: last_daily
        value: "{{_dateUTC}}"

Rules on the data itself

Collections carry their own rules, which limit how far a mistake in one endpoint can corrupt the data model.

  • accessMode: endpoint refuses direct client writes
  • Schema checks on every save: required fields, min: 0, unique ids
  • Per-player save limits reject or clamp floods
YAML Source reference
collections/wallets.collection.yml
kind: collection
id: wallets
collectionType: per-steamid
accessMode: endpoint        # game clients cannot write directly
allowRecordDelete: false
rateLimits:
  mode: player
  savesPerDay: 2000
rateLimitAction: clamp
schema:
  type: object
  required:
    - wallet_id
    - coins
  properties:
    wallet_id:
      type: string
      _unique: true
    coins:
      type: number
      min: 0
      default: 0
      _ledger: true

Combat checks that limit a modded client

Start combat stamps the server time and reads the zombie's health from game values. Finish combat recomputes the damage from the weapons table, checks that the hits fit the weapon's fire rate and the client clock, then pays out once.

  • Damage comes from the weapons table, never from the client
  • TOO_MANY_HITS when hits outrun the fire rate since the server-stamped start
  • CLOCK_SKEW beyond 2 s; a replayed finish gets NO_COMBAT

Lightweight authority for an RPG, without simulating the fight on a dedicated server. The checks bound what a client can claim; they cannot prove a hit landed.

Full example with start-combat
endpoints/finish-combat.endpoint.yml
kind: endpoint
id: finish-combat
method: POST
input:
  type: object
  properties:
    hits:
      type: number
    client_time_ms:
      type: number
  required:
    - hits
    - client_time_ms
steps:
  - id: player
    type: read
    collection: players
    key: "{{steamId}}"
  - id: in_combat
    type: condition
    check:
      field: player.combat.started_ms
      op: exists
    onFail:
      status: 409
      error: NO_COMBAT
  - id: weapon
    type: lookup
    source: values
    table: weapons
    where:
      field: weapon_id
      op: "=="
      value: "{{player.combat.weapon_id}}"
    required: true
  - id: fight
    type: compute
    values:
      damage: "{{input.hits}} * {{weapon.damage}}"
      elapsed_ms: "{{_unixMs}} - {{player.combat.started_ms}}"
      max_hits: "floor({{fight.elapsed_ms}} / {{weapon.fire_interval_ms}}) + 1"
      clock_skew_ms: "abs({{input.client_time_ms}} - {{_unixMs}})"
      xp: "{{player.combat.zombie_level}} * {{values.combat.xp_per_zombie_level}}"
  - id: zombie_dead
    type: condition
    check:
      field: fight.damage
      op: ">="
      value: "{{player.combat.zombie_hp}}"
    onFail:
      status: 400
      error: ZOMBIE_ALIVE
  - id: hits_possible
    type: condition
    check:
      field: input.hits
      op: "<="
      value: "{{fight.max_hits}}"
    onFail:
      status: 400
      error: TOO_MANY_HITS
  - id: clock_ok
    type: condition
    check:
      field: fight.clock_skew_ms
      op: "<="
      value: "{{values.combat.max_clock_skew_ms}}"
    onFail:
      status: 400
      error: CLOCK_SKEW
  - id: reward
    type: write
    collection: players
    key: "{{steamId}}"
    ops:
      - op: inc
        path: xp
        value: "{{fight.xp}}"
        reason: Zombie kill
      - op: set
        path: combat
        value:
          ended_ms: "{{_unixMs}}"

Built for agents. Designed for old builds.

A modern backend that coding agents can operate, designed to keep the games already in players' hands running.

Agent-driven development

sbox-ns mcp gives Claude Code, Cursor and other coding agents the tools you have: set up the server, write and dry-run endpoints, read request logs, errors and records.

  • Runs over SSH or locally on stdio. Nothing new listens on the network.
  • Read-only by default. Definition writes, data writes and deletes are each opt-in.
  • JSON output from every CLI command, and a Claude Code plugin with setup and debugging skills.

Questions

More in the documentation and on GitHub.

Can players cheat their currency or items?

Network Storage limits this when game data stays behind endpoints. Collections set to accessMode: endpoint refuse direct writes from game clients with ENDPOINT_ONLY, and changes go through endpoint steps that run on your server: balance checks, prices from game values, once-per-day conditions, combat checks against weapon stats and the server clock. These checks bound what a client can claim; they cannot prove a hit landed or rule out every kind of cheating.

A player host only ever holds the public key, so it cannot call dedicated-only endpoints either. The dashboard's authority check lists any data a client could still change directly.

What are game values?

Named numbers and tables that your game and your server both read: weapon damage, item catalogs, prices, drop rates and reward amounts. Edit them in your server's dashboard or set them over its API.

The game loads every group and table with one NetworkStorage.GetGameValues() call; endpoints read the same numbers with {{values.*}}, so the client can predict a result and the server checks the claim against the same numbers.

What happens to older builds when I change game values?

Publishing a build snapshots its endpoints, collections and game values. Builds still in players' hands keep running against their own snapshot while it is inside its support window. Requests with no revision header, or with an unknown or expired revision, use live values. A missing snapshot resource can fall back to live values.

Push to staged to ship changes with your next build, or push to live to change the live values for every build not pinned to a supported snapshot. Pushing to live does not overwrite supported snapshots. Player records are always shared live data.

Player-hosted or dedicated: which should I use?

Start player-hosted: it costs nothing to run game sessions, and the rules still live on your backend. Add a dedicated server when you want tournaments, seasons or other modes worth protecting; it holds a secret key for dedicated-only endpoints. One project can serve both at once.

Do I need to change my game code?

No. Games use the existing Network Storage library for s&box. Point NetworkStorage.Configure at your server's URL with your project ID and public key. Server updates keep published game builds working within their support window, so updating the backend does not normally require republishing your game.

What does it cost?

The server is free and open source (AGPL-3.0). You pay your own VPS provider; a VPS around $5 a month can be a starting point for a small game, depending on your workload. There is no signup, subscription or required telemetry.

Which databases does it support?

SQLite by default, with no setup. Switch to PostgreSQL when you need it. Export your configuration and data at any time for backups or to move servers.

Does my server depend on sboxns.com?

Only to create your free name and to update it when your IP changes. With a public IP, players connect to you directly and Bunny DNS answers the lookup; with a tunnel, Cloudflare carries the traffic to you. If sboxcool.com goes down, your existing name keeps working. You can also use your own domain and skip sboxns.com entirely.

Where is my admin panel?

Open https://YOUR_NAME/login to sign in and /dashboard to manage your server. For the first sign-in, run sbox-ns admin login-link on the server and open its single-use link. There is no /admin/login route.

Can coding agents manage it?

Yes. sbox-ns mcp serves the Model Context Protocol over stdio, locally or through SSH, for Claude Code, Cursor and other agents. Agents can read everything; saving definitions, writing player data and deleting are each off until you turn them on.

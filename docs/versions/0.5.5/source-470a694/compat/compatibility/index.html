Library and server compatibility

How server updates keep published games working.

On this page

Non-breaking release rulesAutomated gatesCertification: certify once, re-test on fundamental changeWhen s&amp;box evidence is requiredRoute root and storage versionsClient identity and response contractEndpoint errors for library callersTest evidence, not guessed compatibilityOperator impact and opt-in enforcementSafe binary rollback is a separate guaranteeOn the owner&#39;s server: preflight, watch, roll back

Server releases and game-library releases are independent. Updating the backend must not require republishing an otherwise working game. Library version, package revision, game revision, API version (v3) and database schema version are different identifiers; never compare them as one version.

Tracking: server epic #57 and library tracker #6. Backend/client contracts link S1 #58 ↔ L1 #7, S3 #60 ↔ L2 #8, and S6 #63 ↔ L3 #9. GitHub dependency links, not prose alone, define the implementation order.

#Non-breaking release rules

  • Patch releases preserve existing request syntax, response meanings, error codes, authentication, save semantics and defaults. New fields/capabilities are additive. Follow the existing operator-version rules in releasing.md; a server version bump does not authorize breaking the game API.
  • A rename introduces the replacement while continuing to accept the old form. Keep actual translation logic at the API boundary; do not scatter version checks through storage/endpoint execution. Record why the old form exists and its linked deprecation issue. Do not create empty compatibility abstractions ahead of a real rename.
  • Project secrets (ns.secrets.get, schema version 11) are additive: a new script API member, a new table, and no change to existing requests, responses, or errors. Existing scripts and game clients are unaffected; a script that calls ns.secrets.get needs a server with this release.
  • Deprecation is a warning, not a rejection and not a removal schedule. All public library methods and endpoints, and their meanings, are preserved indefinitely by default: no instant deprecation, no removal, no scheduled deletion. Warnings never authorize removal. Announced sunsets, if any, are informational only. An editor-constructor incident is not evidence that published games are incompatible.
  • A removal needs a replacement already released in the library, matching issues in both repos, a migration guide, real old/new library test evidence, an impact review including unidentified clients, and a separate explicit owner-approved multi-year migration decision. Unknown clients are not proof that everyone upgraded. Prefer retaining v3 and adding a new API generation over altering existing v3 syntax. Any eventual removal is an explicitly migration-gated release, never a surprise patch or routine unattended update.
  • Security/data-loss emergencies can use a narrow, advisory-linked block. Do not turn ordinary obsolescence into a security block. Player game-revision enforcement is separate from library compatibility; players cannot replace the library inside a published game.

#Every compatibility-affecting PR

Link the parent server/client issues, counterpart PR, dependency and priority (compat, priority: P0/P1/P2). State whether the change is additive, deprecated or removal; which existing clients remain accepted; the replacement and sunset; and the request/response and database implications. A library counterpart must be merged/released before a backend removal depends on it. Include SQLite/PostgreSQL corpus results and update the tested matrix evidence. Run the unchanged legacy path, not only a newly versioned client. Reviewers must reject a shortened notice, a patch-only syntax change, or an untested removal.

#Automated gates

These run without anyone remembering to. They are ci-only evidence: hosted runners cannot start the s&box editor GUI, so the green Compat engine leg is the certification for every server change and for every library change in Code/ and Editor/. The contract leg holds changes back; the engine leg additionally certifies every non-GUI pattern it exercises (see Certification). A native editor run is not a gate for PRs or merges; it is reserved for library releases and engine parity checks (see When s&box evidence is required).

Where Check Blocks
Server PR and main Compat gate (compat-matrix.yml): the parity corpus on the change, diffed against the approved stable reference and against the latest release; library version headers; the real library inside s&box (newest Facepunch/sbox-public, -mcp dedicated server) for every library in compat/library-targets.json Any unlisted wire difference. Any library that passes on the latest release and fails on the change (regression). A library failing on both is reported as an engine/library problem, not blamed on the change.
Server release The same gate inside release.yml, before anything is built or signed Publishing. Passing libraries go into the signed release.json testedLibraries.
Server nightly The same gate on main with the newest engine Nothing; opens or updates a compat issue on a regression, a contract failure, or a library that now fails on the released server too (an s&box update broke it).
Library PR Its own required Compat gate: public API diff (held without compat: breaking-approved), the PR's library inside s&box against the latest server release, the oldest supported one (the library's MinServerVersion) and server main, and an Editor evidence check for Code//Editor/ changes that passes when every Compat engine leg is green (no native run and no label needed) See the library's docs/compat-gate.md.
Library publish The revision sync tags each published sbox.game revision r<revision>; the newest three are picked up by latest:3 here and by the library's nightly published-revision leg Nothing on sbox.game itself; a break shows up as a nightly compat issue in either repo.

main requires Compat gate plus the build, test, smoke and secret-scan checks. Administrators can still merge past a red check for an urgent fix; say why in the PR.

An intentional wire change is not a failure to work around: add the difference to tests/parity/intentional-differences.json with a reason in the same PR, so review sees exactly what older games will receive. The newest three published revisions are tested automatically; pin an older revision that players still run in compat/library-targets.json (as git:<sha>) when it drops out of that window. A pinned build with a documented defect that never worked on any server lists those check ids in knownFailures with a link to the library issue: when it also fails on the latest release and its only failures on the change are those ids, the verdict is known (reported, not counted as upstream). Any other failing check on the change still gets the normal verdict, so the pin keeps guarding everything else.

#Certification: certify once, re-test on fundamental change

Both sides are LTS: games embed the library for months and self-hosted servers update independently. A certified pairing is the unit of trust. Certify it once with real evidence, then hold that certification until a fundamental change forces re-testing. Do not re-certify the same pairing on every release, and do not extend a certification to a pairing that was not exercised.

A certification is one tested row: exact server version and source commit, library version and package revision (or null when genuinely unassigned), library source, s&box engine build, operating system, backend kind, database providers actually exercised, a result, and evidence URLs (run logs/artifacts, both-repo PRs/issues). There are two kinds of evidence:

  • Engine legs (GH Actions), the certification for PRs, merges and server releases. The Compat engine leg runs the real library inside the real s&box engine (newest Facepunch/sbox-public built from source, -mcp dedicated server, no editor GUI) against the change and the latest release. A green engine leg certifies every non-GUI pattern it exercises, including the library's Code/ and Editor/ paths the harness can script (for example legacy revision-init shape, save/load round trip, endpoint success/error path, game values, secret-key gate). These rows are recorded with result ci-only (no native editor GUI ran) and the run URL as evidence. For a source-built engine, name the sbox-public commit.
  • Native editor run (Steam build), reserved for two checks. (1) Library release: one native Windows s&box editor run (Steam-interactive sbox-dev.exe, on a non-GH-Actions runner) of the library version being published, recorded as a pass row before that version is published to sbox.game / Library Manager. This is where the Setup and Sync Tool windows and other GUI-only surfaces (Library Manager install/update, Play-in-editor panels, media-capture UX) are checked. (2) Engine parity: periodically, and when Facepunch ships a notable engine update, confirm that the GH-Actions source-built engine and the live Steam engine give the same e2e results, and record it as a matrix row or a note that names both engine identities (the sbox-public commit and the Steam build). Neither check gates a PR or a merge.

HTTP-parity-only runs (no s&box code at all) never certify a pairing. A certified request pattern covers that pattern only; new patterns need new rows.

Fundamental changes invalidate affected certifications and MUST be re-tested before release. Treat these as fundamental on either side: request/response shapes, error codes/envelopes, authentication/authorization behavior, save/endpoint/query/game-value semantics, defaults, rate-limit or revision behavior, added/removed/renamed endpoints or library public methods, identity parsing, capability advertisement, version-policy evaluation, migration assumptions, or supported-provider changes. Internal refactors with no wire, semantic or storage-contract change do not invalidate certification, but still require the unchanged parity corpus and SQLite/PostgreSQL suite.

Library public methods and endpoint support are LTS surface. Do not rename, remove, narrow or change the meaning of a library method, endpoint, field, error code or auth requirement without a shipped replacement, both-repo compat issues/PRs, a migration guide, a separate explicit owner-approved multi-year migration decision, real old-client and new-client evidence, and an impact review covering unidentified traffic. Reviewers MUST reject silent removals, narrowed support, renames without translation, shortened notice, patch-only syntax changes, and any fundamental change without new certification rows. When in doubt, keep the old form and add side-by-side.

#When s&box evidence is required

Pull requests, merges and server releases are certified by the GH-Actions Compat engine legs: the real library inside the real s&box engine, headless. A green engine leg is sufficient evidence for every server change and for every library change in Code/ and Editor/. No native Windows s&box editor run is required to open, merge or release a server change, and no PR or issue label tracks one. A native run is reserved for a library release (one pass row for the version being published) and for periodic engine parity checks. The rule is about the surface, not about how big or risky a change feels.

GUI surface means anything the dedicated harness (tools/sbox-cli-e2e, -mcp dedicated server) does not script: the Setup and Sync Tool windows, Library Manager install/update, Play-in-editor panels and logs, media-capture UX, and any Editor/ GUI code. A change has GUI surface when it alters what those windows show or do, or when its acceptance can only be observed through them. GUI-surface changes merge on green engine legs; the native run that checks them happens before the library version that ships them is published.

Classify every PR's client-visible surface (the PR template asks for it):

Class Meaning Evidence
None Request and response bytes, headers, status codes, error codes and defaults the library sees are identical to the previous release for every request it can send. Owner console, CLI, installers, updater, DNS/tunnel, monitoring and alerting, demo, storage internals, additive migrations whose reads and writes return the same results, performance, docs. No s&box run. Required evidence is that the claim is true (below).
Additive, off by default New fields, headers, endpoints, capabilities or behaviors that appear only when the owner turns something on. The default-off path is byte-identical. Green Compat gate (contract + engine leg) on the commit before it is documented as supported to game developers. The default-off path needs no native run. Native checks for any GUI behavior belong to the library release that ships it.
Changed Any difference for a request the library can already send: shapes, field meanings, error codes or envelopes, auth/session/encryption handling, save/endpoint/query/value semantics, rate-limit or revision behavior, defaults, status-header or capability values the library reads. GH Actions. Green Compat gate (contract + engine leg) on the commit, plus the old-client replay in Every compatibility-affecting PR. No native run is needed to merge. A library release that carries the change publishes only after its native pass row exists (see below).
Library code Any change in the library repo's Code/ or Editor/ (runtime, Sync Tool, Setup). GH Actions. Green Compat engine legs on both repos' gates cover the paths the dedicated harness exercises. Pure logic is also covered by library unit tests. A native run is required before the library release that ships the change (it checks the Setup and Sync Tool windows and other GUI-only paths), not before the PR merges.

"Identical" must be shown, not asserted. For a None or default-off claim attach:

  1. the parity diff against tests/parity/stable-reference.json with no unrecorded differences (scripts/smoke.sh --out ..., then sbox-ns-parity diff ...), and a note if tests/parity/intentional-differences.json changed;
  2. SQLite and PostgreSQL both green for the touched storage path, and scripts/smoke.sh clean;
  3. for an additive migration, the additive tag in both drivers and a legacy-request replay against the migrated database (docs/database.md, "Rollback-safe migrations");
  4. a regression test for the default-off path when new behavior is gated by a project or server setting (for example: a legacy request with no x-ns-revision-id performs no extra lookup and returns the same body).

If any of these cannot be produced, the change is not None; classify it honestly and require the test. Unknown clients and older libraries are always in scope: "the current library behaves the same" is not enough when an older published game could see a difference.

Server-only runs never certify. HTTP tests, the parity corpus and fake-handler tests exercise no s&box code and can never certify a Changed or Library code change. The Compat engine leg is not server-only: it is the real library inside the real s&box engine, so a green engine leg certifies every non-GUI pattern it exercises. GUI-only behavior that the harness cannot script is checked by the native run before a library release.

No native run is needed to open, merge or release a server change. Do not apply pending-sbox-editor-test to a PR or an issue. For a library release, the native pass row is a release step: record it before the version is published, as described in releasing.md. Say in the release notes which rows exist.

#Route root and storage versions

The library default route root is planned to change from /v3 to /api (library counterpart #36, not shipped). The root is configurable. Released libraries call /v3/.... There is no runtime capability switch: a library does not detect server routes and change root by itself. Servers that do not serve /api (every release before the /api root, targeted for server 0.5.5 and not yet released) need the library configured to root v3 explicitly.

  • /v3/* and /api/v3/* are the only permanent surface for existing library methods and endpoints. They are kept indefinitely with their existing meanings; neither is deprecated or removed.
  • New features are served at /api/* only. They are not duplicated under /v3, and an API-only route never gains a /v3 alias later.
  • For every existing non-reserved family, /api/{family}/* mirrors /v3/{family}/* through the same handler, auth, limits, metering, policy and error capture. Usage and analytics stay keyed by the canonical /v3 path; the request log keeps the original path.
  • /api/pages and /api/network-storage are legacy routes with their existing meanings (for example POST /api/network-storage/{projectId}/save-failure). They are not mirrors.
  • /api/storage is version-aware. A valid x-ns-library-version of 1.2.0 or newer uses the canonical current v3 storage handlers. A missing, malformed (not SemVer or longer than 64 characters) or older value keeps the legacy /api/storage meaning unchanged; do not assume it matches /v3/storage for those callers.
  • Direct HTTP clients that are not the library send x-ns-library-version: 1.2.0 when calling /api/storage to get the uniform storage semantics. The header selects routing only: it is not authentication, and authorization is unchanged.
  • Routing versions (the path prefix and x-ns-library-version) are syntax metadata, never authorization. Keys, accessMode and every other check still decide access.

Older libraries keep calling /v3/.... That stays supported indefinitely: those clients can never be updated, so /v3 is not deprecated and is not removed. /v1 keeps its existing status. /api is additive-only like /v3: a future breaking change ships side by side under new resource names or an explicit generation segment (/api/v4/...), and never changes an existing /api/{path} or /v3/{path} in place.

#Client identity and response contract

The wire headers are described in game-client.md: x-ns-library-version, x-ns-library-revision, x-ns-client-type, x-ns-revision-id, x-ns-engine-version. Missing/invalid versions are the legacy bucket and are advertised as unknown; this is accepted by default. Existing revision-init, heartbeat and analytics JSON already parsed by their handlers can supply the library version (networkStorageVersion, libraryVersion, library_version) and the published game revision (revisionId on a published bundle); a version header takes precedence. The body fallback enriches telemetry, not authentication or a pre-handler enforcement decision. No additional body buffering/parsing is needed. Existing response bodies are unchanged except the additive compat object in /api/server-info (also /v3/server-info). One change is not additive: a Sync Tool or endpoint write whose script the server refuses is now refused with 400 VALIDATION_FAILED, and nothing is written, where it was stored before. Sync preflight fails with PREFLIGHT_VALIDATION_FAILED for the same scripts. The refusal body adds a top-level diagnostics array with the file, line and column; see Sync refusals.

The project's Errors tab captures the same request identity (library/context, package revision and game revision). Errors raised outside an HTTP request have legacy/unknown context and no revision; no player IDs or API keys are added.

Responses include x-ns-server-version and x-ns-library-status: unknown, supported, outdated, deprecated, unsupported or blocked. A known latest version and deprecation sunset are advertised in x-ns-library-latest and x-ns-library-sunset when relevant. The explicit project minimum can override the status of a refused request to unsupported.

GET /api/server-info (also /v3/server-info) adds compat.library with nullable minimum, recommended, latest, supported legacy, deprecated, blocked, knownBroken and tested, plus compat.matrixUrl. Null means no released/tested version has been established; it does not mean an invented 1.0.0. Recommendations and sunsets do not expire working games automatically.

The shipped matrix is immutable and offline: no unsigned remote source can impose a library minimum or a remote kill switch. The release feed may carry a libraryCompat overlay, but the overlay only ever tightens the reported status on servers that have not been updated (for example to flag a library with a security problem). It never refuses a request: enforcement reads the embedded matrix only, and requests without a parseable library version are never refused by any rule. Header identities and player counts are self-reported, not a security boundary; a hostile caller can spoof versions. Keep all real authentication/authorization checks.

#Endpoint errors for library callers

Endpoint-route errors (/v3/endpoints/...) reach a library caller as HTTP 200 with the real status in the body (issue #152). The library reads only the body of a 2xx response, so the status it needs has to be in the body. A caller is a library caller when it sends a non-empty x-ns-library-version, a recognised x-ns-client-type (game, editor or dedicated), or a body security object. Every other client keeps the real HTTP status and the flat body it has always received. Non-endpoint routes return the real status to everyone.

Identification by published library build (from each revision's source). The signal is on the request, not the version string:

Build Headers Body
r238672 x-ns-client-type on every request security and _endpointSlug on POST
r422519 x-ns-client-type on the authenticated path only security and _endpointSlug on POST
r423774 x-ns-library-version and x-ns-client-type on the authenticated path only security and _endpointSlug on POST

The dedicated-server public-key path sends no library header in r422519 or r423774. A body-less GET on that path cannot be identified and keeps the real status. POSTs on that path are identified by their body.

A library caller receives:

{"ok":false,"status":401,"error":{"code":"UNAUTHORIZED","message":"...","requestId":"..."},"message":"...","_requestId":"..."}
  • status is the status the error would have had. error.requestId, _requestId and the X-Request-Id header carry the same ID.
  • _revisionStatus appears when the revision handshake applies.
  • retryAfterSeconds appears on rate-limit (429) errors, and the Retry-After header is also set.
  • security and retrySafe: true appear only on SECURITY_* gate denials.
  • A 5xx keeps only a generic message and no stored writes.
  • Not mirrored from the reference envelope: _auth, timing, storageDelta, docsUrl, hints and the legacy detail field.
  • Usage stats and request logs record the real status, not 200.

The server advertises library-error-envelope in the capabilities of /v3/server-info. The parity corpus gates the expectations of the affected steps on that capability (ifCapability), so a server without it keeps the base expectations. The #152 differences are listed in tests/parity/intentional-differences.json with the reason "Library envelope (#152)".

#Test evidence, not guessed compatibility

compat/library-matrix.json is embedded in the server and validated against library-matrix.schema.json. It currently records supported legacy clients and the separate old-editor incident, not fictional library releases or editor passes.

Each published libraries entry records version, status, numeric revision (when assigned by s&box), released and minServer. The legacy entry instead uses the revisions range. Deprecation and blocked-version ranges use space-separated SemVer comparisons (=, <, <=, >, >=, or an exact version); all comparisons must match. Every token is validated by the release gate and when loading the embedded policy, even when an earlier comparison would not match the current client. Version values also respect the server parser's 64-character limit and non-negative 32-bit major/minor/patch components.

A tested row records the exact server version/source commit, library version/package revision and source, s&box engine build, operating system, backend kind, database providers, pass/fail/ci-only, and evidence URLs. Follow editor-test-plan.md. Evidence links should identify the run, logs/artifacts and related PRs/issues, with secrets removed. Compat engine legs are recorded as ci-only rows; native editor runs are pass rows. Automated HTTP parity alone is not a row.

python3 scripts/compat-release.py
python3 scripts/compat-release.py --matrix /path/to/release-evidence.json \
  --server 0.x.y --commit TESTED_SOURCE_COMMIT \
  --baseline /path/to/previous-release-matrix.json \
  --policy-source compat/library-matrix.json

Release notes require matching-commit evidence for the recommended library: a ci-only row from the green Compat engine legs, or a pass row from a native editor run. The gate accepts a ci-only row by default. When no pass row exists, the generated notes say the release is CI-only and that no native editor run is recorded; the green engine legs are the certification. The library release checklist requires the native pass row for the library version being published; this server gate accepts either row type. dotnet test validates the committed matrix and exercises these gates; Python 3 is required. The PowerShell companion scripts/compat-tested-with.ps1 renders the same rows as the "Tested with" release-notes table; it is a notes renderer, and its -Gate switch applies the same matching-commit check. The authoritative release gate is scripts/compat-release.py (see releasing.md). For a deprecated library entry with a later supported successor, the gate enforces sunset floors: the recorded sunset must be at least six months after the successor's released date and, when announced is recorded, at least 90 days after that announcement. Announced sunsets cannot be shortened against the baseline. These floors limit how early a date may be written; a recorded sunset is informational and never authorizes removal (see Non-breaking release rules).

A source commit cannot contain its own hash in a newly committed evidence row. Keep the release evidence as a detached build/release artifact after testing the final source commit; record it in the repo subsequently. Never change the tested commit to the later bookkeeping commit. Use --matrix for that artifact, and attach the generated table and matrix to the release. A binary's tested advertisement only includes records actually embedded for its version; matrixUrl also points to the maintained evidence history, not an authenticated policy override. The maintainer owns release-workflow attachment and the native editor runs for library releases and engine parity checks.

Validate a detached artifact with --policy-source: it may change tested evidence only, not the matrix policy that was exercised by the tests. Embed that validated artifact without changing the source commit:

dotnet publish src/SboxNetworkStorage.Server -c Release \
  -p:Version=0.x.y \
  -p:LibraryCompatibilityMatrix=/absolute/path/to/release-evidence.json

Without this build property, the committed matrix is embedded. The build property supplies a build input, not a runtime overlay or an unsigned policy refresh. Keep the artifact with the signed release outputs.

#Operator impact and opt-in enforcement

Open Project → Clients (/dashboard/projects/{id}/clients) or run:

sbox-ns project clients PROJECT_ID --days 30
sbox-ns project clients PROJECT_ID --days 30 --json

The read-only MCP tool is project_clients. Reports group library/package revision, client context and game revision, showing request count, approximate distinct players, last seen, status/sunset and affected share. The dashboard previews a proposed minimum without changing it. Saving a non-empty/new minimum requires owner authentication, an antiforgery token and explicit acknowledgement that older published games that report a library version will be blocked; the change is audited. Clear the minimum to restore default acceptance. A backend update never sets it. Clients that report no library version are never blocked by any rule. Updates through this dashboard invalidate the policy cache immediately; external project-setting changes can take up to 30 seconds.

Project JSON stores libraryMinimum and optional libraryAlertPercent; both are absent by default. A refusal is HTTP 426 using the library's existing structured error envelope, and only ever for two reasons: the project's explicit minimum, or a blocked range in the embedded matrix (never the feed overlay):

{"ok":false,"error":{"code":"LIBRARY_UNSUPPORTED","message":"Update the library and republish the game."}}

Advisory blocks use LIBRARY_BLOCKED with the advisory in the message. Missing/invalid keys and unauthorized management keys retain their original 401/403 paths, and management diagnostics and recovery (Pull, Test Live, revision-init) stay reachable. The s&box runtime can hide 4xx bodies; use response headers, server logs and the library-side update UI, not an assumption that every old game can display this message.

Traffic is buffered in memory, flushed once per minute and at graceful shutdown, and retained locally for 90 UTC days. The collector accepts at most 2,000 identity groups per UTC day/process and 2,000 pending groups; flushing does not reset the daily budget. Overflow is best-effort telemetry loss, never a failed game request. Restarting resets the in-process cardinality/drop counters; the CLI counter belongs to its own process, while the live dashboard shows the running server's counter. Database queries do not silently truncate the report.

Distinct-player sketches merge across requests, flushes and days with approximately 3.25% relative error. No raw player IDs or hashes are persisted in this compatibility table. Unidentified players are not counted. Percentages are by requests, not players; this traffic cannot prove every installed game upgraded. Setting the project's alert threshold enables rate-limited Discord/SMTP alerts through the existing alert sink when at least 100 requests in a flushed batch meet the affected percentage. Notifications remain opt-in; nothing is sent to a hosted analytics service.

#Safe binary rollback is a separate guarantee

Schema rollback (preserved-data downgrades, schema floors, rollback --keep-data) is documented in database.md. It certifies schema/config compatibility, not game behavior. For release notes, capture each prospective target's successful compatibility --json result against the release's schema/config and pass it as --rollback-report /path/to/report.json to compat-release.py; without reports, the generated notes explicitly certify no preserved-data target.

#On the owner's server: preflight, watch, roll back

CI cannot cover every library build in every published game, so each server also guards its own games (details in self-hosting.md):

  • Before an update, sbox-ns update compares the release's signed release.json testedLibraries with the library versions this server's games sent in the last 30 days. A library with at least 1% of requests that the release lists as fail stops the update (--ignore-compat overrides); untested builds are a warning. Unattended updates hold such a release.
  • After an update, every request is counted per library version and server version (client_outcomes_hourly, additive migration v7; telemetry only, nothing on the wire changes). For 48 hours the server compares each library's error rate (5xx plus 4xx other than 401, 403, 409 and 429) with the previous release; a jump of at least 10 points and 2x, with at least 50 requests on both sides, is a regression. It sends one critical alert with the rollback commands, shows it in sbox-ns doctor and the owner console's Server page, and sbox-ns update verify prints the table (exit 5 on a regression).
  • Rolling back is one command: sbox-ns rollback --keep-data when every migration since is additive, otherwise sbox-ns rollback (restores the pre-update backup). Unattended updates roll back by themselves on a regression when that keeps all data (updates.auto_rollback, default on).

These are self-reported library versions: they detect breakage, they never authenticate anything or refuse a request.
